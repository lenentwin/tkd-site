# Развёртывание в ISPmanager / Cludex

Инструкция подготовлена для инфраструктуры из задания: PHP 8.3, Nginx + PHP-FPM, MySQL. На конкретном аккаунте Cludex настройка не выполнялась. Публичная страница провайдера не подтверждает состав PHP-расширений и настройки конкретного MSK-2; их нужно проверить в панели. Пароли и секреты в чат или GitHub передавать не нужно.

## 1. Разместить файлы и ограничить публичную директорию

В ISPmanager откройте существующий сайт **api.mft39.ru**. Сначала сохраните резервную копию его текущих файлов. Основной сайт mft39.ru, его DNS и GitHub Pages не меняйте.

Рекомендуемая структура, где USER заменяется настоящим именем владельца из панели:

```text
/var/www/USER/data/www/api.mft39.ru/
  config.example.php
  config.local.php          # создаётся только на сервере
  src/                      # весь каталог из backend/src
  migrations/001_auth.sql
  bin/cleanup.php
  public/                   # содержимое backend/public
    index.php
    health/index.php
    auth/yandex/start/index.php
    auth/yandex/callback/index.php
    api/me/index.php
    api/logout/index.php
```

Фактический путь может отличаться. Смотрите «Каталог сайта» в панели, не копируйте USER буквально. В настройке **публичного каталога сайта** укажите `/public`; document root должен стать `.../api.mft39.ru/public`. Наличие отдельного публичного каталога описано в [документации ISPmanager](https://www.ispmanager.com/docs/ispmanager/adding-and-configuring-a-website).

На хостинг загружайте public/, src/, config.example.php, migrations/ и bin/. docs/ и README можно оставить вне public. Не загружайте tests/, .git, .env frontend, .cache, node_modules, dist или локальные архивы шрифтов.

Если публичный каталог изменить нельзя: разместите src/, config.example.php, config.local.php, migrations/ и bin/ в отдельной приватной директории домашнего каталога, вне document root **всех** сайтов. В существующий document root скопируйте только содержимое backend/public. В его index.php замените `$privateRoot = dirname(__DIR__);` абсолютным путём к приватной директории. Остальные PHP-обёртки не меняйте. PHP-FPM должен иметь доступ к этой конкретной директории: при ограничениях open_basedir попросите провайдера добавить её, не открывайте весь сервер. Если провайдер не даёт безопасно отделить конфигурацию от web root, такой вариант развёртывания пока заблокирован; не кладите секреты в public с надеждой на .htaccess.

Не удаляйте прежние файлы без резервной копии. Если панель создаёт default index.html внутри public, сохраните его копию вне web root и установите **index.php первым индексным файлом**. Не включайте листинг каталогов. Права по возможности: config.local.php 600, приватные папки 700/750 с доступом владельца PHP-FPM; не 777. Не оставляйте backup-копии PHP, дампы и ZIP в public.

## 2. PHP, HTTPS, маршруты и логи

Выберите PHP 8.3, режим Nginx + PHP-FPM. Нужны стандартные расширения pdo_mysql, curl, json и актуальное хранилище CA для исходящих HTTPS. Composer и Node на сервере не нужны. Убедитесь, что Let's Encrypt покрывает api.mft39.ru и HTTP перенаправляется на HTTPS. Приложение не доверяет произвольному X-Forwarded-Proto: сервер должен передавать настоящий HTTPS в PHP.

Без rewrite маршруты обслуживают физические директории с index.php. Проверьте `/health/`, `/health/index.php`, `/api/me/`, `/auth/yandex/start/`. Если `/health/` не исполняет index.php, исправьте индексную страницу в настройках сайта либо используйте прямые `/index.php` адреса. Для callback ниже предусмотрен такой вариант.

Для **этого API-сайта** в «Журналы сайта» выберите **«Не использовать журнал»** до первого настоящего OAuth-входа: access/error логи веб-сервера могут сохранять query с code/state. Приложение пишет только фиксированное `MFT39 backend: request_failed`, без exception/SQL/HTTP body. Если аудит запросов обязателен, согласуйте с поддержкой формат без query, Cookie, Authorization и тел запросов/ответов. Не отправляйте журналы API в зарубежную аналитику. Отключение журналов и отдельный публичный каталог есть в документации ISPmanager, но доступность этих полей на MSK-2 проверяется владельцем в панели. Если скрыты, нужна помощь поддержки; это обязательная проверка перед реальным входом.

Выключите кеширование PHP/прокси для API; не кешируйте профиль и callback. Не подключайте CDN с хранением запросов пользователей. D1/Workers/Functions не используются. Не меняйте DNS существующего backend для выполнения этой инструкции.

## 3. Создать MySQL и таблицы

В ISPmanager → «Базы данных» создайте отдельную MySQL-базу и пользователя с новым случайным паролем. Запишите параметры только в config.local.php на сервере. Выберите utf8mb4, если панель предлагает кодировку.

Откройте phpMyAdmin из панели, выберите **эту новую базу**, импортируйте backend/migrations/001_auth.sql один раз. Создаются users, auth_sessions и auth_rate_limits. Автоматического выполнения миграций при HTTP-запросах нет. При повторном импорте существующие таблицы не удаляются, импорт завершится ошибкой уже существующей таблицы. Не удаляйте таблицы для устранения ошибки; проверьте, что миграция уже применена. Обновления схемы должны идти отдельными миграциями с резервным копированием.

Если доступны отдельные права, runtime-пользователю достаточно SELECT/INSERT/UPDATE/DELETE только на эти таблицы; DDL выполняется отдельно при миграции. Не используйте root. В общедоступном репозитории нет пользовательских данных или дампа БД.

## 4. Создать приложение Яндекс OAuth

На https://oauth.yandex.ru создайте приложение для MFT39 и платформу «Веб-сервисы». Зарегистрируйте Redirect URI **точно**:

```text
https://api.mft39.ru/auth/yandex/callback
```

Проверьте, что Nginx обрабатывает его: допустим единственный переход к `/auth/yandex/callback/` с сохранением query. Если перенаправления/каталоги недоступны, зарегистрируйте вместо него `https://api.mft39.ru/auth/yandex/callback/index.php` и задайте **такое же** значение YANDEX_REDIRECT_URI в config.local.php. Код разрешает только эти варианты и вариант с завершающим `/`.

Используется code flow с PKCE S256. Сервер передаёт redirect_uri и verifier при обмене, проверяет client_id ответа, если он присутствует. Никакого отключения state/PKCE для обхода ошибок.

Не включайте email, телефон, дату рождения, фото, имя/фамилию, пол и другие необязательные права. Стандартный API возвращает id и client_id. Если приложение допускает регистрацию без дополнительных прав, YANDEX_SCOPE оставьте пустым. Если интерфейс Яндекса требует право идентификации, используйте минимальное login:info, запишите YANDEX_SCOPE='login:info'; все дополнительные поля ответа сервер игнорирует и не сохраняет. Не добавляйте другие права, чтобы обойти настройку. Требования к публикации/модерации приложения зависят от настроек Яндекса и должны быть выполнены владельцем.

Client ID и Client Secret скопируйте только в приватный config.local.php. [Официальная документация code flow/PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url), [поля API профиля](https://yandex.ru/dev/id/doc/ru/user-information).

## 5. Заполнить приватную конфигурацию

Скопируйте config.example.php в config.local.php рядом с src/, вне public. Заполните YANDEX_CLIENT_ID, YANDEX_CLIENT_SECRET, YANDEX_REDIRECT_URI, DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD, FRONTEND_URL. FRONTEND_URL строго `https://mft39.ru`.

RATE_LIMIT_KEY: новая случайная строка минимум 64 символа, например результат `php -r "echo bin2hex(random_bytes(32));"`, выполненного локально в терминале или через закрытый SSH. Не создавайте веб-страницу-генератор секретов. Сроки по умолчанию: SESSION_TTL=28800, SESSION_IDLE_TTL=1800, OAUTH_TTL=300. Значения имеют допустимые границы, проверяемые конфигурацией. Пароли не передавайте параметрами URL/CLI, которые сохраняются в истории.

Если панель умеет задавать environment PHP-FPM, можно использовать одноимённые переменные: они имеют приоритет над config.local.php. .env frontend сервер не читает. В GitHub Actions/Repository secrets, Pages или VITE_* Client Secret и пароль MySQL **не помещаются**.

В планировщике ISPmanager добавьте запуск раз в 10 минут с CLI PHP 8.3 и абсолютным путём `.../bin/cleanup.php`. Узнайте путь к php83 в панели/у поддержки; не используйте выдуманный системный путь. Задача удаляет истёкшие сессии и старые rate buckets. Само истечение сессий проверяется на каждом запросе и не зависит от запуска cron. Ошибки cleanup не содержат секретов.

## 6. Проверить backend до включения frontend

1. GET `https://api.mft39.ru/health/`: HTTP 200, только `{"status":"ok"}`. Это не тест БД.
2. GET `https://api.mft39.ru/api/me/` без cookie: **401** и unauthenticated. Это уже проверяет загрузку конфигурации/соединение с БД. 503 означает, что нужно проверить приватные настройки, расширения, права и миграцию.
3. OPTIONS `/api/logout/` с Origin:https://mft39.ru, Access-Control-Request-Method:POST и Access-Control-Request-Headers:X-CSRF-Token: **204**, точный Allow-Origin и Credentials:true. С Origin:https://example.invalid ответ **403** без Allow-Origin.
4. GET callback без state/code: **400 invalid_state**, не stack trace. Это проверка маршрута, а не доказательство успешного OAuth.
5. Убедитесь, что `/config.local.php`, `/config.example.php`, `/src/Config.php`, `/migrations/001_auth.sql`, `/tests/run.php` снаружи недоступны (404/403, никаких исходников/SQL). Не создавайте диагностический phpinfo в public.
6. Откройте `/auth/yandex/start/` обычной навигацией. Должен быть настоящий переход на oauth.yandex.ru, state и code_challenge_method=S256, без client_secret в URL. Cookie API имеет все требуемые флаги. Отказ на Яндексе не создаёт пользователя.
7. Завершите вход владельцем через реальный аккаунт Яндекса. Callback должен выполнить внешний обмен, создать одну строку users и собственную auth_sessions; перенаправить на https://mft39.ru/account без токенов и code/state. Не копируйте адрес callback с code в чат/скриншот/логи.

Для пункта 7, пока frontend не включён, `/account` покажет старое состояние отсутствия подключения. Проверить уже установленную серверную сессию можно в консоли **основного сайта mft39.ru**:

```js
const r = await fetch('https://api.mft39.ru/api/me/', { credentials: 'include' });
console.log(r.status, await r.json());
```

После входа ожидается 200 и ваш внутренний id/role=user. Не отправляйте содержимое профиля или cookie третьим лицам. Повторный вход должен сохранить id и одну строку users. Изменение query `role=head_trainer` не меняет роль. Проверьте выход с полученным csrfToken через POST и credentials:include, затем me должен вернуть 401; предыдущая cookie перестаёт работать на сервере. Неправильный CSRF должен давать 403 и сохранять сессию.

## 7. Включить существующий frontend после приёмки

Код backend и адаптер frontend опубликованы в main по подтверждению владельца; исходная ветка codex/yandex-auth сохранена. После ручной проверки backend в GitHub → Settings → Secrets and variables → Actions → **Variables** задайте только публичные значения:

```text
VITE_API_BASE_URL=https://api.mft39.ru
VITE_AUTH_ENABLED=true
```

Запустите Deploy MFT39 to GitHub Pages через Run workflow для main. Либо выполните новую сборку с этими значениями в вашем процессе публикации. По умолчанию флаг выключен: одна строка API URL не включает авторизацию. В dev прежняя демонстрация сохраняется только при выключенном реальном адаптере; при включённом флаге demo storage игнорируется.

Откройте /login: кнопка должна вести на настоящий Яндекс. /account загружает server profile; сеть/ошибка API даёт явную недоступность. Выход ждёт реального ответа сервера и не показывает фиктивный успех при сетевой ошибке. Формы записи и анкеты этим этапом не включаются. Стили и композиция страниц сохранены; изменены только относящиеся к авторизации тексты/состояния.

Cookie API недоступна JavaScript. Не переносите её на Domain=.mft39.ru и не добавляйте CORS *. Никаких OAuth-токенов в localStorage или URL frontend. CSP альтернативного Cloudflare разрешает connect только к этому API origin; GitHub Pages файл _headers не интерпретирует.

## 8. Что доказывает реальную работу

Зелёные автоматические тесты проверяют код с имитацией только Яндекса и с настоящим MySQL. Они не доказывают настройку Cludex или живого OAuth-приложения. Реальная приёмка требует успешного внешнего code exchange на api.mft39.ru, нового собственного session ID, строки в российской БД, ответа me=200 и выхода с последующим me=401. Пока владелец не выполнил эти действия, live OAuth отмечается как непроверенный.

Для отката frontend выключите VITE_AUTH_ENABLED и пересоберите Pages. При остановке backend сохраните private config и БД в защищённой российской резервной копии; не удаляйте DNS/таблицы/приложение Яндекса без отдельного решения.
