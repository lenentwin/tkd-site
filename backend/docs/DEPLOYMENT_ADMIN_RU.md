# Обновление003: административная панель MFT39

Обновляется существующая MySQL mft39_auth и PHP API на российском хостинге. Новая БД/D1 не создаётся; DNS/SSL/callback не меняются. Миграции на действующем сервере разработчик не применяет. Сначала проверить копию базы в России.

## Порядок

1. В ISPmanager сохранить закрытый backup mft39_auth и PHP-файлов в России. Проверить читаемость и восстановление. Записать действующий privateRoot из API index.php, сохранить config.local.php и права PHP-FPM/open_basedir. Не отправлять дампы/секреты в GitHub/чат/внешние логи.
2. В phpMyAdmin выбрать существующую mft39_auth. Проверить SELECT VERSION(), InnoDB/utf8mb4, SELECT version FROM club_schema_version WHERE id=1. Эта инструкция предполагает2 и уже применённые001/002. При версии1 сначала отдельно002 по DEPLOYMENT_CLUB_RU.md. Не импортировать001 повторно. CI проверяет PHP8.3/MySQL8.4; другую СУБД не менять вслепую.
3. Подготовить новые PHP в приватной staging-папке. Полный набор src/Club включает Admin, Permissions, Profile. Сохранить config.local.php; не заменять его примером, не менять client ID/secret/redirect URI.
4. Выбрать короткое окно обновления API, при необходимости штатный режим обслуживания с HTTP503. Записи не должны выполняться посреди смены версии. Публичный frontend может оставаться доступным. Не очищать историю для «чистой установки».
5. phpMyAdmin → mft39_auth → «Импорт» → migrations/003_admin_profiles.sql → UTF-8 → выполнить один раз. Миграция не удаляет старые данные и не угадывает год рождения. DDL не откатывается одной транзакцией. При частичной ошибке остановиться и сравнить схему/backup, не повторять весь импорт наугад и не удалять таблицы.
6. Обновить приватные src/ и bin/. Файлы PUBLIC в этом обновлении не менялись: существующие публичные обёртки и их privateRoot сохраняются, перезаливать их не требуется. PUBLIC-архив нужен лишь для восстановления отсутствующих обёрток. При его использовании index.php должен сохранить прежний фактический privateRoot: dirname(__DIR__) подходит только когда src прямо в родительском каталоге public; при разнесённых папках нужен проверенный абсолютный приватный путь. При необходимости перечитать PHP-FPM/OPcache средством хостинга; не создавать публичный debug/reset endpoint.
7. Runtime DB-пользователю нужны прежние auth-права; SELECT/INSERT/UPDATE/DELETE для рабочих club_students/applications/payments/student_guardians/trainer_halls/user_permissions; SELECT/INSERT/UPDATE для club_application_batches/device_tokens; SELECT/UPDATE club_access_lock; прежние INSERT/SELECT/UPDATE users. Для club_audit нужны SELECT/INSERT и UPDATE только для процедуры обезличивания; DELETE не нужен. Runtime не нужны DDL/FILE/SUPER/TRIGGER. Не использовать root. Выдавать права конкретному проверенному DB-пользователю средствами владельца.
8. Проверить schema version3, /health/index.php →200, /api/me/ без сессии →401. В веб-сессии bootstrap даёт schemaVersion3/capabilitiesVersion3 и корректный месяц/залы; native bearer сохраняет schemaVersion2 с capabilitiesVersion3. Проверить CORS/CSRF. Снять обслуживание после успешной проверки.
9. Если admin уже есть, войти им. Если нет, один раз в приватной phpMyAdmin найти собственную запись и проверить принадлежность по Яндекс ID, а не совпадению ФИО. Закрытый CLI: php bin/staff.php role ВАШ_ID admin, сначала preview, затем с --apply. CLI не открывать через HTTP. Обычный user теперь не видит свой ID в UI; первоначальное назначение выполняет владелец сервера, автоматически оно не происходит.
10. Только после готовности API опубликовать frontend ветки codex/admin в main. GitHub Pages workflow собирает dist, CNAME mft39.ru/base=/ сохраняются. Форма года рождения требует схемы3, поэтому frontend последний. Не выкладывать PHP/SQL на Pages. До готовности backend действующая опубликованная версия остаётся прежней.
11. В PWA осознанно выбрать «Обновить» после завершения заполнения форм. Проверить реальный Яндекс вход/выход, профиль, admin/не-admin, несколько залов, архив/restore, заявку и помесячную оплату. Удаление проверять только на синтетической карточке тестовой копии, не на реальном ученике.
12. Проверить отсутствие ПД, Cookie, Authorization, OAuth query и JSON-тел в логах. Не подключать внешнюю аналитику. Секреты и данные остаются на российском сервере.

## Архивы и пути

PUBLIC содержит только backend/public, BACKEND содержит src/bin/migrations/config.example.php, DOCS содержит инструкции, FRONTEND содержит готовый dist. Ни один ZIP, SQL, tests, docs, .git, .env или config.local.php не должен находиться в public. В пакете нет существующего config.local.php: он сохраняется на сервере.

## Имя и старые ученики

Если Яндекс не передал имя, проверить право login:info в существующем приложении. Не запрашивать email/телефон/аватар/дату рождения, не создавать новый client ID и не менять callback. Расширение разрешения при необходимости выполняет владелец; может понадобиться повторное согласие/вход. До этого ФИО можно заполнить вручную. После правки новый вход его не перезапишет.

Старые birth_year остаются NULL. Родитель уточняет год в «Мои тренировки», staff с разрешением статуса в карточке. До уточнения старый возраст показан как снимок. Годовой возраст не считается точным возрастом до дня рождения.

## Откат

До приёма новых данных допустимо восстановить согласованный backup PHP и БД при остановленных записях. После новых заявок нельзя слепо возвращать старый дамп: они потеряются. Предпочесть исправление схемы и совместимый код. Старый backend со строгим schemaVersion2 несовместим с club_schema_version3; не возвращать его отдельно. Возврат frontend сам по себе003 не отменяет.

Контракт и ограничения: ADMIN_API.md. Это подготовка обновления, не заявление об установке на production.

FRONTEND-архив соответствует GitHub Pages, включая404.html и CNAME. Для Cloudflare использовать отдельную обычную сборку без prepare-pages.mjs, как описано в README, а не импортировать этот Pages-артефакт как универсальный.
