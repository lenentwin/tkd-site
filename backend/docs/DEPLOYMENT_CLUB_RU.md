# Установка системы учеников и оплат на api.mft39.ru

Это обновление существующей PHP 8.3 / MySQL `mft39_auth`, не создание новой базы. Доступа к Cludex/ISPmanager у разработчика нет; действующая база не менялась. Архив MFT39-Club-Backend.zip подготовлен отдельно; SQL автоматически по HTTP не запускается. Сначала выполните установку на копии базы в России, затем на действующей базе с резервной копией. Не выгружайте реальные ПД в GitHub или зарубежные сервисы.

## Порядок обновления

1. В ISPmanager сохраните резервную копию текущих PHP-файлов, конфигурации и `mft39_auth` в приватной папке российского сервера. Запишите действующий путь `$privateRoot` из public/index.php. Не скачивайте/публикуйте секреты в чат. Копия содержит ПД и должна оставаться закрытой.
2. Убедитесь, что сервер действительно MySQL 8.0+ (SELECT VERSION()), InnoDB/utf8mb4, PHP 8.3 с PDO MySQL/cURL/JSON. CI проверяет MySQL 8.4; MariaDB и более старые MySQL отдельно не проверялись. Не меняйте движок действующего хостинга вслепую: при иной версии сначала нужна проверка совместимости.
3. В phpMyAdmin выберите существующую `mft39_auth`. Убедитесь, что 001_auth уже применена (users/auth_sessions/auth_rate_limits). Импортируйте **только migrations/002_club.sql**, один раз. Не создавайте заново users, не импортируйте тесты. Миграция добавляет роль admin и club_* таблицы; старые роли, пользователи и сессии сохраняются. DDL в MySQL не откатывается одной транзакцией. При частичной ошибке остановитесь и сравните фактическую схему, не удаляйте таблицы и не повторяйте весь импорт наугад.
4. Загрузите src/, config.example.php и bin/ в существующий приватный backend-каталог вне document root. **Сохраните существующий config.local.php**, его секреты и права. Из public/ загрузите только публичные файлы в document root API. В новом public/index.php восстановите фактический `$privateRoot`, если прежний хостинг использовал абсолютный путь. Копирование default dirname(__DIR__) поверх нестандартного приватного пути без проверки сломает вход.
5. Обязательно загрузите public/api/club/index.php. Сохраните остальные OAuth/me/logout/health обёртки. Не размещайте migrations/, bin/, tests/, docs/, ZIP/SQL/config.local.php в публичной папке. Никаких .htaccess для сокрытия случайно опубликованных секретов. Публичным остаётся только содержимое public/.
6. Runtime DB-пользователю нужны прежние права auth и SELECT/INSERT/UPDATE на club_*; на club_audit достаточно SELECT/INSERT. Назначения/DDL выполняются владельцем отдельно. Не используйте root в config.local.php. Если конфигурация owner CLI имеет расширенные права, держите её вне сайта и уберите доступ после назначения.
7. Проверьте HTTPS, отсутствие proxy/cache на API и прежние безопасные настройки логов (DEPLOYMENT_RU.md). Нельзя логировать тела JSON, Cookie, Authorization, OAuth query или отправлять ошибки/ПД во внешнюю аналитику. DNS, Yandex callback/client settings и действующий config.local.php менять для этого обновления не требуется.

## Назначить тренеров и залы

Роль на сервере, клиент не может назначить её себе. Пользователь сначала входит через Яндекс и сообщает владельцу номер аккаунта из «Мои данные». В приватном backend-каталоге через SSH/PHP 8.3:

```sh
php bin/staff.php role 42 trainer
php bin/staff.php role 42 trainer --apply
php bin/staff.php grant 42 chelnokova
php bin/staff.php grant 42 chelnokova --apply
```

42 здесь **пример**, используйте проверенный реальный ID. Без --apply только проверка и просмотр, изменений нет. Доступные halls: chelnokova, city, school10. grant/revoke допускается для trainer; head_trainer/admin видят все залы без grant. Аналогично `role ID head_trainer`, `role ID admin`, `role ID user`, `revoke ID hall`, сначала preview. Все применённые изменения пишутся в club_audit с source owner_cli; actorId=null означает владельца сервера через закрытый CLI, а не фиктивного администратора. CLI не умеет удалять ученика/историю или обходить веб-авторизацию.

## Проверка после установки

- /health/index.php →200; /api/me/ без сессии →401.
- /api/club/index.php?resource=bootstrap без сессии →401; в действующем кабинете →schemaVersion 2, верные currentMonth/serverTime и назначенные залы.
- OPTIONS физического club/index.php с Origin https://mft39.ru и заголовками content-type,x-csrf-token,idempotency-key →204. Чужой Origin →403. Не лечить CORS через wildcard или отключение CSRF.
- На отдельной тестовой копии: создать заявку, проверить actual MySQL pending/trial/guardian; повтор не дублирует; чужой тренер не видит; принять/отклонить; статус отдельно от оплаты; исправление с причиной/audit; история сохраняется при inactive; две параллельные правки дают409.
- После проверки копии войдите реальными аккаунтами владельца/тренера и убедитесь в назначениях. Не загружайте в production синтетические CI fixtures. Первую настоящую заявку проверяйте с согласия её владельца только на российском сервере.

Frontend: Node24, npm ci, npm run build, output dist, GitHub Pages/основной домен mft39.ru и base=/ сохранены. VITE_AUTH_ENABLED=true и VITE_API_BASE_URL=https://api.mft39.ru. Новых секретов или Cloudflare Functions/D1 нет. До успешного bootstrap схемы 2 сайт держит отправку недоступной. После загрузки backend и миграции она станет доступна автоматически. SPA fallback и CNAME не менялись.

## Если потребуется откат

Не удаляйте новые таблицы и не откатывайте ENUM на три роли после появления admin. Сначала отключите/верните frontend или публичную club-обёртку, сохранив данные; старый OAuth-код совместим с прежними таблицами. Возврат к проверенным PHP-файлам делать из приватной копии, сохранив правильный privateRoot/config.local.php. При проблеме схемы сначала остановить новые записи и разбирать с владельцем, а не запускать DROP/TRUNCATE. Бэкапы также остаются в России.
