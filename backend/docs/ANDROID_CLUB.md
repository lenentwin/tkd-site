# Подключение Android к MFT39 Club API

Исходников Android (`.kt`, `.java`, Gradle, AndroidManifest.xml) в этом репозитории нет. APK не собирался и не менялся. Ниже контракт интеграции, а не утверждение о готовой интеграции приложения. Backend и сайт используют существующую российскую MySQL `mft39_auth` через PHP; прямой MySQL из телефона запрещён.

## Вход тренера

1. Тренер входит через Яндекс на mft39.ru. Владелец заранее назначает роль/grants на сервере (DEPLOYMENT_CLUB_RU.md).
2. В кабинете «Ученики и заявки» → «Доступ для приложения» создаёт личный доступ, указывает своё устройство. Секрет показывается один раз и не сохраняется браузером.
3. Экран подключения в Android должен принимать этот ключ в скрытое поле без аналитики, автосохранения и логирования. Отправлять только в заголовке `Authorization: Bearer ...` на HTTPS `api.mft39.ru/api/club/index.php`. Не использовать query, cookie из WebView или общий ключ в BuildConfig/APK. После ввода очистить поле и временный clipboard; не передавать ключ по мессенджеру.
4. Доступ действует 8 часов, отзывается владельцем из веб-кабинета, проверяет действующую роль и назначения на каждом запросе. На 401 удалить доступ и предложить повторное подключение. Продление через старый bearer отсутствует: новый доступ создаётся через действующую веб-сессию. На 403 удалить недоступные данные и сообщить о правах. Телефон не назначает себе роль.
5. Хранить токен и локальный кэш в приватном хранилище приложения, шифруя ключом из Android Keystore; не хранить сам bearer «как Keystore key». Исключить секреты/ПД из backup, crash reports, HTTP interceptors, debug logs, внешних SDK и скриншотов экрана подключения. При выходе удалить локальные ПД и токен. Keystore защищает криптографические ключи: [официальная документация Android](https://developer.android.com/privacy-and-security/keystore).

## Данные и действия

Полные схемы, версии, параметры и примеры: CLUB_API.md.

- bootstrap → роль/назначенные залы/schemaVersion/currentMonth/serverTime/scopeVersion.
- students (все страницы; staff без view=own) → зачисленные ученики. Filter active/all/trial/permanent/inactive.
- applications?status=pending (все страницы) → новые заявки; application-decision + expectedVersion → принять/отклонить.
- student-status + expectedVersion → trial/permanent/inactive.
- payments → история календарных месяцев; payment + version соответствующего месяца + expectedCurrentMonth → ручная отметка.
- changes → scoped аудит; использовать для уведомления об обновлении, а не как единственный источник состояния.

Запросы без Origin, с Authorization; для POST JSON. Не отключать проверку HTTPS-сертификата. Не добавлять mysql connector, пароль БД или Yandex client_secret. Нужен сетевой timeout и явное состояние отсутствия соединения.

## Offline и смена месяца

Ключ оплаты в кэше: `(studentId, YYYY-MM)`, а не единственный boolean paid. Месяц всегда определяется в `ZoneId.of("Europe/Kaliningrad")`. При соединении сохранить serverTime и соответствующий `SystemClock.elapsedRealtime()`; вычислять текущее серверное время прибавлением прошедшего monotonic elapsed (включая сон), затем брать YearMonth в указанной зоне. После перезагрузки телефона monotonic якорь больше невалиден: используйте календарь устройства в этой зоне только как предварительную оценку, показывайте устаревшее/неизвестное состояние до синхронизации, а не безусловное paid. При подозрении на неверные часы также не показывайте подтверждённую актуальную оплату.

Если текущий месяц отличается от месяца сохранённой paid-отметки, на экране сразу «Не оплачено» либо «Нет актуальных данных», даже без интернета и CRON. Никогда не копируйте paid в новую запись. Проверьте Nov30 21:59:59Z→22:00Z, Dec31 21:59:59Z→22:00Z, выключение приложения до следующего месяца, сон и перезагрузку телефона.

## Синхронизация и конфликты

На старте, возврате на экран, восстановлении сети, смене месяца/прав и периодически получать полный scoped snapshot со всеми страницами. Заменять старые доступные наборы, удалять потерявшие доступ элементы. Перечитать текущие месячные записи и выбранную историю. Во время загрузки и при ошибке не называть устаревший кэш актуальными данными.

Пагинация и audit cursor не являются транзакционным снимком: возможны вставки до UUID cursor и поздний commit с меньшим audit ID. Поэтому периодическая полная перечитка обязательна; changes служит сигналом. Не ограничиваться только delta polling. При обнаружении изменений во время первоначальной постраничной загрузки повторить сверку snapshot, дедуплицируя по ID.

Отложенное действие хранит исходные expectedVersion и expectedCurrentMonth. При выходе в сеть сначала перечитать сервер и показать изменения тренеру. Не заменять expectedVersion на новую автоматически. На 409 показать обе ситуации и запросить новое явное решение. Не делать last-write-wins, blind UPSERT, бесконечные ретраи 409 и перенос намерения «оплачено» с прошлого месяца на новый. Неотправленную правку отмечать как локальную, не как сохранённую в MySQL.

## Приёмка в отдельном Android-проекте

Подключить контракт к существующему HTTP-клиенту; удалить старые прямые DB/общие admin credentials, если они были. Проверить два тренера разных залов, head_trainer, отзыв/истечение токена, родительский аккаунт, чужой UUID, потерю сети, принятие/отклонение, деактивацию с сохранением истории, одновременную правку сайта и телефона и смену года. До прохождения этих проверок интеграция APK остаётся незавершённой. Синтетические тестовые записи удалять только из отдельной тестовой БД, никогда из production для «чистоты» проверки.
