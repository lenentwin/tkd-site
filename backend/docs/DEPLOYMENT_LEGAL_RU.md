# Подключение юридических документов и подтверждений

Статус поставки: подготовленный черновик, **не включён на production**. Основная база остаётся `mft39_auth`; новую базу создавать не нужно. Production-миграция автоматически не выполняется. DNS, SSL и настройки Яндекс OAuth не меняются.

## Подготовка и локальная проверка

1. Ознакомиться с `docs/legal-drafts/README.md` и согласовать перечисленные сведения с руководством.
2. Исправить полные исходные тексты `docs/legal-drafts/*.md`. Для новой редакции установить новую уникальную версию в `registry.json`; не менять утверждённый текст под старой версией.
3. После реального утверждения указать `status: approved`, `approvedBy` (ответственный/ссылка на решение), `approvedAt` (YYYY-MM-DD) для каждого документа. Не заполнять эти поля фиктивно. Согласие отдельно от соглашения; политика доступна без галочки.
4. Выполнить `npm run legal:generate`, `npm run legal:release-check`, `npm run lint`, `npm test`, `npm run build`. Проверка выпуска сейчас должна завершиться отказом: тексты ещё черновые.
5. Проверить на тестовом PHP/MySQL и в браузере сценарии отказа, первого входа, повторного входа, смены версии, записи нескольких детей, прямого HTTP без согласий, выхода и отсутствия интернета. Тестовые одобрения в автоматических тестах синтетические, в production bundle их нет.

## Обновление через ISPmanager

1. Сделать и проверить восстанавливаемую резервную копию текущей базы и PHP-файлов. Уточнить АКТИВНУЮ private-папку и document root: на хостинге ранее было две копии backend. Не удалять ни одну наугад. Рабочая `public/index.php` должна по-прежнему указывать на соответствующий private root.
2. В phpMyAdmin выбрать существующую `mft39_auth`. Проверить `SELECT version FROM club_schema_version WHERE id=1;` (ожидается 3). Проверить наличие `legal_schema_version` через список таблиц. Если таблиц согласий ещё нет, один раз импортировать `backend/migrations/004_legal_consents.sql`. Если она уже применена, `SELECT version FROM legal_schema_version WHERE id=1;` должно вернуть 1. Не импортировать повторно и не использовать DROP. DDL MySQL не откатывается обычным ROLLBACK; при частичной ошибке остановиться и исследовать её.
3. Загрузить в АКТИВНУЮ private-папку обновлённые `src/`, `resources/legal-documents.json` и `config.example.php`. Сохранить свой `config.local.php`, секреты не копировать из примера. Существующие `public/`-обёртки не изменены. Важно загрузить НОВУЮ `resources/` вместе с PHP: она содержит общие тексты/версии.
4. Пока идёт поэтапное обновление, оставить `'LEGAL_ENFORCEMENT' => 0` в private config.local.php (или окружении). Значение по умолчанию 0. Существующий вход/кабинеты работают как раньше; старое согласие заявки сохраняется. Миграция не создаёт подтверждений за пользователей и не признаёт старую общую галочку принятием новых документов.
5. После утверждения и проверки выпуска опубликовать frontend из того же коммита/JSON. Для GitHub Pages использовать действующий workflow: Node24, npm ci, npm run build, prepare-pages, dist. Кастомный домен и Vite base / сохранены.
6. Проверить четыре публичных маршрута `/legal/terms`, `/legal/privacy`, `/legal/user-consent`, `/legal/guardian-consent`, ссылки футера/входа и обновление PWA.
7. Только затем включить `'LEGAL_ENFORCEMENT' => 1` на PHP. Повторно проверить обычный и тренерский/административный аккаунты. Пользователь без двух актуальных подтверждений получает 403 на приватные ресурсы, но может получить состояние документов, подтвердить их или выйти. Если версии frontend/PHP расходятся, принятие блокируется до обновления клиента, а не имитирует успех.
8. Запись ребёнка после включения требует отдельной снятой по умолчанию галочки для каждого ребёнка; подтверждение с version/hash связано с application_id и student_id в одной транзакции. Родительское подтверждение/согласие аккаунта нельзя подменить чужим ID.

## API

Существующий endpoint `https://api.mft39.ru/api/club/index.php`:

- `GET ?resource=legal`: только собственное состояние, четыре type/title/version/hash/status, enforcement/required/canAccept, собственные подтверждения account. Ответ `no-store, private`, без IP/UA/токенов.
- `POST ?resource=legal-accept`: JSON `{ "documents": [{"type":"terms","version":"...","hash":"SHA256","accepted":true},{"type":"user_consent","version":"...","hash":"SHA256","accepted":true}] }`. Cookie + точный Origin + X-CSRF-Token. При обновлении одной редакции допустимо отправить только её, если другое действующее подтверждение уже есть. Ответ как GET legal. Любые userId/date/поддельные версии отклоняются.
- `POST ?resource=applications`: существующий формат, у каждого несовершеннолетнего в `students[]` дополнительно `guardianConsent: {type:"guardian_consent",version,hash,accepted:true}`. Отсутствие хотя бы одного подтверждения откатывает весь пакет. Старые consent/consentVersion остаются как совместимые технические поля, но не заменяют новое подтверждение при enforcement1. У новых пакетов при включённом механизме batch.consent_version содержит служебный маркер `legal-acceptance-refs-v1`, а не ложную отметку о принятии старого текста. Юридическое подтверждение и точная дата находятся только в legal_acceptances.
- `GET /api/me/`: дополнительное поле `legal: {required,enforcement,canAccept}`. Сессия Яндекс остаётся существующей; повторный OAuth не нужен для принятия.

Ошибки: `legal_required` (403), `legal_documents_unavailable` (403, включая черновик), `legal_migration_required` (503), `legal_confirmation_required`/`guardian_consent_required` (422), `legal_browser_required` (403). CSRF, роли, hall scope и блокировки продолжают действовать.

Таблица `legal_acceptances` хранит серверный user_id, type, полную версию, SHA256 текста, UTC confirmed_at, application_id/student_id для ребёнка. Время и ID не принимаются от клиента; уникальное ограничение исключает дубль подтверждения. Старые версии сохраняются. IP/браузер не добавляются. Приватное API и подтверждения не попадают в CacheStorage, IndexedDB или localStorage. Offline недоступны подтверждения/запись, статические тексты доступны с пометкой о невозможности проверить актуальность.

## Android и возврат к предыдущему состоянию

APK в репозитории отсутствует. Native-токен не может оформлять новое согласие пользователя за него: при `legal_required` приложение должно предложить вход на сайт, показать требование и после подтверждения повторить синхронизацию. Нельзя показывать отказ как успешную операцию или обходить gate общим ключом. Формат schemaVersion3 web/2 native не изменён; добавлен контракт ошибок. Для native-записи несовершеннолетнего нужен такой же отдельный proof, полученный от законного представителя, а не галочка тренера.

При проблеме после активации: восстановить совместимые frontend/PHP из резервной копии и проверить конфигурацию/версии. Осознанный возврат LEGAL_ENFORCEMENT0 отключает новый gate и возвращает прежний режим обработки; это решение оператора, а не исправление юридических оснований. Таблицы и уже полученные подтверждения сохранять. Не откатывать базу разрушением таблиц/удалением данных. Не запускать тестовые fixtures на production.
